# Security Review — 커밋 전 타입 · 보안 점검

이 스킬은 리팩토링 완료 후 커밋 전에 실행한다. 타입 오류, 의존성 취약점,
환경 변수 노출을 스캔하고 결과를 심각도별로 분류하여 개발자에게 보고한다.
개발자 승인을 받은 항목만 수정하며, 자동으로 판단하여 코드를 바꾸지 않는다.

## 입력

`$ARGUMENTS`로 이슈 번호를 받는다. 예: `/security-review 1`

이슈 번호는 `git diff main...HEAD --name-only -- src/`로 이번 이슈에서 변경된
파일 범위를 특정하는 데 사용한다. 타입 오류 보고 시 이 범위 밖의 기존 오류는
별도로 표기하여 구분한다.

## 실행 순서

### 1단계: 타입 검사

```bash
npx tsc --noEmit 2>&1
```

출력을 파싱하여 파일별 타입 오류 목록을 수집한다.

- 오류가 없으면 "타입 검사 통과"로 기록하고 2단계로 진행
- 오류가 있으면 각 오류를 파일 경로, 라인 번호, 에러 코드, 메시지로 정리

### 2단계: 의존성 취약점 검사

```bash
npm audit 2>&1
```

출력을 파싱하여 취약점 목록을 수집한다.

- 취약점이 없으면 "의존성 취약점 없음"으로 기록하고 3단계로 진행
- 취약점이 있으면 각 항목을 패키지명, 심각도(critical/high/moderate/low), 설명으로 정리

### 3단계: 환경 변수 노출 검사

`.env` 파일이 프로젝트 루트에 존재하면 그 안의 변수명을 추출한다.
그런 다음 `src/` 디렉토리에서 해당 변수 값이 하드코딩되어 있는지 확인한다.

```bash
# .env가 있으면 변수명 추출 후 src/에서 값 검색
grep -rn "변수값" src/ --include="*.ts" --include="*.tsx"
```

추가로 아래 패턴도 검사한다:

| 패턴                 | 위험 | 예시                         |
| -------------------- | ---- | ---------------------------- |
| API 키/토큰 하드코딩 | 높음 | `const API_KEY = 'sk-...'`   |
| 비밀번호 하드코딩    | 높음 | `password: 'admin123'`       |
| 내부 URL 하드코딩    | 중간 | `fetch('http://192.168...')` |

`.env` 파일이 없으면 하드코딩 패턴 검사만 수행한다.
localhost URL(예: `http://localhost:3001`)은 개발 환경 목 서버이므로 무시한다.

### 4단계: 결과 분류 및 보고

수집된 모든 결과를 세 가지 등급으로 분류하여 개발자에게 보고한다.

#### 분류 기준

**즉시 수정 필요** (빌드 실패 또는 보안 위험):

- 이번 이슈 변경 파일의 타입 오류 (빌드가 깨짐)
- critical/high 심각도 의존성 취약점
- API 키, 비밀번호 등 민감 정보 하드코딩

**권장 수정** (코드 품질 저하):

- moderate/low 심각도 의존성 취약점
- 내부 URL 하드코딩 (환경 변수로 분리 권장)
- 이번 이슈 범위 밖 기존 파일의 타입 오류

**무시 가능** (false positive 또는 의도된 패턴):

- devDependencies의 취약점 (프로덕션 미포함)
- localhost URL (개발 환경 목 서버)
- `process.env.VITE_*` 형태의 정상적인 환경 변수 접근

#### 보고 형식

```
보안 점검 결과 (issue #1):

■ 즉시 수정 필요 (2건)
  1. [타입 오류] src/hooks/useTagEditor.ts:15 — TS2345: Argument of type ...
  2. [보안] src/api/notes.ts:3 — API 키가 소스에 하드코딩됨

■ 권장 수정 (1건)
  1. [취약점] lodash@4.17.20 — moderate: Prototype Pollution

■ 무시 가능 (1건)
  1. [무시] src/api/notes.ts:3 — localhost:3001은 개발용 목 서버

위 분류가 맞는지 확인해 주세요.
"즉시 수정 필요" 항목을 처리할까요?
```

**개발자 승인을 받은 후에만** 5단계로 진행한다.

### 5단계: 승인된 항목 수정

개발자가 승인한 "즉시 수정 필요" 항목만 수정한다.

- **타입 오류**: 오류 원인을 분석하고 최소한의 수정으로 해결
- **보안 이슈**: 하드코딩된 값을 환경 변수로 분리하거나 제거
- **의존성 취약점**: `npm audit fix` (--force 없이)로 안전하게 업데이트 시도

각 수정 후 해당 검사를 다시 실행하여 해결 여부를 확인한다.

### 6단계: 재스캔 및 클린 확인

모든 수정이 끝나면 1~3단계를 다시 실행하여 클린 상태를 확인한다.

```bash
npx tsc --noEmit 2>&1
npm audit 2>&1
npm test 2>&1
```

테스트도 함께 실행하여 수정 과정에서 회귀가 발생하지 않았는지 확인한다.

결과를 개발자에게 최종 보고한다:

```
재스캔 결과:

✓ 타입 검사: 오류 0건
✓ 의존성 취약점: critical/high 0건
✓ 환경 변수 노출: 없음
✓ 테스트: 전체 N개 통과

커밋 준비 완료.
```

잔여 "권장 수정" 또는 "무시 가능" 항목이 있으면 함께 안내한다.

## 제약 사항

- **개발자 승인 필수.** 분류 결과를 보고한 뒤 승인 없이 코드를 수정하지 않는다.
  자동 판단으로 코드를 바꾸면 의도치 않은 동작 변경이 발생할 수 있다.
- **테스트 파일 수정 금지.** `*.test.ts`, `*.test.tsx` 파일은 절대 수정하지 않는다.
  보안 점검의 목적은 구현 코드의 안전성 확인이며, 테스트는 점검 범위 밖이다.
- **npm audit fix --force 금지.** `--force`는 메이저 버전 업그레이드를 강제하여
  breaking change를 유발할 수 있다. 안전한 `npm audit fix`만 사용하고,
  그래도 해결되지 않는 취약점은 개발자에게 보고한다.
- **범위 제한.** `git diff main...HEAD --name-only -- src/`로 식별한 파일의
  문제를 우선 처리한다. 범위 밖 기존 오류는 "권장 수정"으로 분류하여 안내만 한다.
