# TDD Green — 최소 구현으로 테스트 통과

이 스킬은 TDD의 Green 단계를 수행한다. Red 단계에서 작성한 실패 테스트를
통과시키는 **최소한의 구현 코드**만 작성한다. 테스트에 없는 기능은 구현하지 않고,
테스트 파일은 수정하지 않는다.

## 입력

`$ARGUMENTS`로 이슈 번호를 받는다. 예: `/tdd-green 1` → issue-1.md 기반으로 구현한다.

## 실행 순서

### 1단계: 실패 테스트 목록 확인

`npm test`를 실행하여 현재 실패 중인 테스트 목록을 파악한다.

### 2단계: collect 실패 감지

시나리오 문서(`docs/features/tag/issue-$ARGUMENTS.md`)의 체크박스(`- [ ]`) 총 건수와
vitest가 보고하는 Tests 수를 비교한다.

- **불일치 시**: import 대상 모듈이 아직 존재하지 않아 vitest가 테스트를 인식조차
  못하는 상태다. 시나리오 문서의 확정 시그니처를 참고하여 **시그니처만 있는 stub 파일**을
  생성한다. stub은 함수/컴포넌트의 export와 타입 시그니처만 포함하고, 내부 로직은
  비워 둔다(훅이면 빈 값 반환, 컴포넌트면 `null` 반환 등).
- stub 생성 후 `npm test`를 다시 실행하여 전체 테스트가 인식되는지 확인한다.

### 3단계: 디자인 컨텍스트 로드

구현 대상에 UI 컴포넌트가 포함되면, 스타일 스펙을 미리 파악해 둔다.
테스트가 요구하는 동작을 충족하면서도 디자인 가이드에 맞는 코드를 작성하기 위함이다.

1. `docs/design-system.md`가 존재하면 읽어서 구현 대상 컴포넌트의 시각적 스펙
   (색상, 간격, 레이아웃, 상태별 표현)을 파악한다.
   - 파일이 없으면 프로젝트 내 디자인 시스템 관련 문서를 탐색한다
     (`docs/design/` 디렉토리, `tokens.md`, `rules.md` 등).
2. `docs/features/{feature}/issue-$ARGUMENTS.md`에 "디자인 참고" 섹션이 있으면
   함께 확인한다.
3. `CLAUDE.md`의 스타일링 컨벤션(Tailwind 유틸리티 클래스 우선 등)도 참조한다.
4. 디자인 문서가 전혀 없으면 이 단계를 건너뛰고 `CLAUDE.md` 컨벤션만 따른다.

### 4단계: 첫 번째 실패 테스트 통과시키기

실패 테스트 목록에서 **첫 번째 실패 테스트**를 선택하고, 그 테스트만 통과시키는
**최소한의 코드**를 작성한다.

- 테스트가 요구하는 동작만 정확히 구현한다. 테스트에 없는 로직을 미리 넣지 않는다.
- UI 컴포넌트 구현 시, 3단계에서 파악한 디자인 스펙을 함께 적용한다:
  - `design.md`에 명시된 Tailwind 클래스를 그대로 사용한다.
  - 레이아웃 구조, 상태별 표현(hover, disabled, active 등)을 따른다.
  - `design.md`에 없는 시각적 요소를 임의로 추가하지 않는다.

### 5단계: 테스트 실행 및 피드백 루프

해당 테스트 파일을 실행하고, 전체 테스트도 함께 실행하여 회귀가 없는지 확인한다.

```bash
npx vitest run <해당 테스트 파일>
npm test
```

- **테스트 통과 + 회귀 없음** → 6단계로 진행
- **테스트 실패** → 에러 메시지를 읽고 원인을 분석하여 코드를 수정한 뒤
  5단계를 다시 실행한다 (최대 5회 반복)
- **5회 반복 후에도 실패** → 실패 원인과 시도한 접근 방식을 개발자에게 보고하고 중단

### 6단계: 시나리오 문서 체크

`docs/features/tag/issue-$ARGUMENTS.md`에서 통과시킨 테스트에 해당하는
체크박스를 `[x]`로 변경한다.

### 7단계: 다음 실패 테스트로 이동

남은 실패 테스트가 있으면 4단계로 돌아가 반복한다.
모든 테스트가 통과할 때까지 이 루프를 계속한다.

### 8단계: 커버리지 측정

전체 테스트 통과 후 커버리지를 측정한다.

```bash
npx vitest run --coverage
```

- 미커버 라인을 확인하고, 시나리오에서 빠진 케이스인지 개발자에게 보고한다.
- **커버리지를 올리기 위한 테스트 추가는 금지한다.** 참고 정보로만 활용한다.

### 9단계: 결과 요약

개발자에게 다음을 보고한다:

- 생성/수정한 구현 파일 목록
- 시나리오별 통과 현황 (총 N개 테스트, N개 통과)
- 커버리지 요약 (라인/브랜치 커버리지 %)
- 미커버 라인이 있다면 해당 내용과 누락된 시나리오 가능성

## 제약 사항

- **테스트 파일 수정 금지.** `*.test.ts`, `*.test.tsx` 파일은 절대 수정하지 않는다.
  Green 단계의 목적은 "기존 테스트를 변경 없이 통과시키는 것"이다.
  테스트를 수정하면 Red 단계에서 합의한 스펙이 변질된다.
- **테스트에 없는 기능 구현 금지.** 실패 테스트가 요구하는 동작만 구현한다.
  "나중에 필요할 것 같은" 기능을 미리 넣으면 YAGNI 원칙을 위반하고
  불필요한 복잡성이 쌓인다.
- **불필요한 추상화 금지.** 헬퍼 함수, 유틸리티, 팩토리 등을 미리 만들지 않는다.
  테스트를 통과시키는 가장 직접적인 코드를 작성한다.
- **디자인 문서 범위 준수.** `design.md`에 명시된 스타일은 적용하되,
  문서에 없는 시각적 요소(그림자, 애니메이션, 추가 색상 등)를 임의로 넣지 않는다.
