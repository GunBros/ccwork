# TDD Refactor — 테스트 보호 하에 코드 구조 개선

이 스킬은 TDD의 Refactor 단계를 수행한다. Green 단계에서 "일단 통과"시킨 코드를
프로젝트 컨벤션에 맞게 정리하고, 중복을 제거하며, 가독성을 높인다.
핵심 원칙: **모든 테스트가 항상 통과하는 상태를 유지**한다.

## 입력

`$ARGUMENTS`로 이슈 번호를 받는다. 예: `/tdd-refactor 1` → issue-1 관련 변경 파일을 리팩토링한다.

## 실행 순서

### 1단계: 프로젝트 컨벤션 파악

`CLAUDE.md`를 읽고 다음을 확인한다:

- 네이밍 규칙 (이벤트 핸들러, props, boolean, API 함수, Context 메서드)
- 컴포넌트 패턴 (named export, Props 인터페이스, 구조분해, early return)
- 상태 관리 패턴 (UI 상태 vs 서버 상태 분리, 낙관적 업데이트)
- API 호출 패턴 (순수 fetch 래퍼, 타임스탬프 주입 위치)
- 스타일링 방식 (Tailwind 유틸리티 우선)
- 코딩 규칙 (.prettierrc 기준)

### 2단계: 전체 테스트 통과 확인

```bash
npm test
```

- **전체 통과** → 3단계로 진행
- **실패 테스트 존재** → 리팩토링을 시작할 수 없다. 실패 현황을 개발자에게 보고하고 중단.
  리팩토링은 Green이 완료된 상태에서만 의미가 있다.

### 3단계: 리팩토링 대상 파일 식별

이번 이슈에서 변경된 src/ 내 구현 파일만 리팩토링 대상으로 삼는다.

```bash
git diff main...HEAD --name-only -- src/
```

결과에서 테스트 파일(`*.test.ts`, `*.test.tsx`)을 제외한 나머지가 대상 파일이다.

### 4단계: 점검 기준에 따라 개선점 도출

대상 파일 각각을 읽고, 아래 5가지 범용 점검 기준으로 검토한다.

#### 점검 기준

| #   | 기준                    | 점검 내용                                                                          |
| --- | ----------------------- | ---------------------------------------------------------------------------------- |
| 1   | 중복 제거               | 같은 로직이 두 곳 이상에서 반복되는가? 공통 함수로 추출할 수 있는가?               |
| 2   | 네이밍 명확성           | 변수, 함수, 컴포넌트 이름이 의도를 드러내는가? 약어나 모호한 이름이 있는가?        |
| 3   | 단일 책임               | 하나의 함수/컴포넌트가 너무 많은 일을 하는가? 분리하면 테스트·재사용이 쉬워지는가? |
| 4   | 불필요한 복잡도         | 매직 넘버, 과도한 중첩(3단계 이상), 불필요한 추상화, 사용되지 않는 코드가 있는가?  |
| 5   | CLAUDE.md 컨벤션 불일치 | 1단계에서 파악한 프로젝트 패턴과 어긋나는 코드가 있는가?                           |

각 파일별로 개선이 필요한 항목을 목록화한다. 개선할 점이 없으면 그 파일은 건너뛴다.

### 5단계: 리팩토링 계획 보고 및 승인 대기

개발자에게 리팩토링 대상 목록을 보고한다:

```
리팩토링 대상:
1. src/hooks/useTagEditor.ts
   - [중복 제거] addTag와 removeTag에서 유효성 검사 로직 중복
   - [네이밍] `val` → `trimmedValue`로 의도 명확화
2. src/components/TagInput.tsx
   - [컨벤션 불일치] Props 인터페이스가 파일 외부에 정의됨
```

**개발자 승인을 받은 후에만** 6단계로 진행한다.
승인 없이 코드를 수정하지 않는다. 개발자가 일부 항목만 승인하면 해당 항목만 진행한다.

### 6단계: 하나씩 변경 → 테스트 → 확인

승인된 개선 항목을 **하나씩** 적용한다. 한 번에 여러 변경을 묶지 않는다.

각 변경마다:

1. 코드 수정
2. 테스트 실행:
   ```bash
   npm test
   ```
3. 결과 확인:
   - **전체 통과** → 다음 항목으로 진행
   - **테스트 실패** → 즉시 변경을 되돌리고(롤백), 다른 접근 방식을 시도한다.
     같은 항목을 2회 시도 후에도 실패하면 해당 항목을 건너뛰고 개발자에게 보고한다.

테스트가 깨진 상태에서 다음 변경으로 넘어가지 않는다.
테스트를 통과시키기 위해 테스트 코드를 수정하지 않는다.

### 7단계: 변경 요약 제공

모든 리팩토링이 완료되면 개발자에게 전후 변경 요약을 보고한다:

```
리팩토링 완료 요약:

✓ src/hooks/useTagEditor.ts
  - [중복 제거] 유효성 검사를 validateTag() 함수로 추출
    Before: addTag, removeTag 각각에 trim + 길이 검사 인라인
    After:  validateTag(value) 호출로 통합
  - [네이밍] val → trimmedValue

✓ src/components/TagInput.tsx
  - [컨벤션 불일치] Props 인터페이스를 파일 내부로 이동

✗ src/components/NoteEditor.tsx
  - [단일 책임] 핸들러 분리 시도 → 테스트 실패로 건너뜀 (사유: ...)

테스트: 전체 N개 통과, 0개 실패
```

## 제약 사항

- **새 기능 추가 금지.** 리팩토링은 외부 동작을 변경하지 않는 내부 구조 개선이다.
  새로운 기능이나 동작을 추가하면 Refactor 단계의 범위를 벗어난다.
- **테스트 파일 수정 금지.** `*.test.ts`, `*.test.tsx` 파일은 절대 수정하지 않는다.
  테스트는 리팩토링의 안전망이며, 안전망 자체를 바꾸면 리팩토링의 의미가 없어진다.
- **src/ 디렉토리 밖 수정 금지.** 설정 파일, 문서, 빌드 스크립트 등은 건드리지 않는다.
- **대상 파일 범위 밖 수정 금지.** 3단계에서 `git diff`로 식별한 파일만 수정한다.
  이번 이슈와 무관한 파일을 "ついでに(겸사겸사)" 정리하지 않는다.
